# 判断ルール（迷ったときの型）

配信中に迷う場面はパターンが決まっている。毎回ゼロから悩まないための判断の型。
ここでは特に **立ち上げ段階（0→1）のリード / 登録獲得** で効く考え方を渡す。
具体値は事業で変わるので、`config.md` に自社の値を持ち、ここは「どう判断するか」として使う。

> 原則：ルールをそのまま押し付けず、**「なぜそうするか」**を理解して事業に合わせて応用する。

## 1. コンバージョンイベント

- **まず標準イベントを使う**（登録完了・購入・購読など、Meta が理解しやすい標準の名前）。独自イベントは後回し。
- **「ボタンを押した人」より「実際に完了した人」を CV に置く**ほうが、学習の質が上がる（ただし件数は減るので、初期は手前のイベントで学習を稼ぐ判断と併用）。
- なぜ：Meta の最適化は「CV に到達した人の群れ」に似た人を探す。CV 定義がズレると学習がまるごと歪む。

## 2. 言語 / 地域ターゲティング

- **コード値を推測で入れない。必ず API で実際の意味を確認してから設定する。**
- 自分の市場の言語・地域を**漏れなく**指定する（方言・表記違いで標準ユーザーを除外しないよう注意）。
- なぜ：言語コードの取り違えは「意図と違う対象に全額配信」という、最も痛い事故につながる。

## 3. 配信面の自動拡張（外部アプリ面など）

- **初期はいったん絞る**。データが少ないうちに広げると、安いが質の低い面にお金が流れがち。
- 成果が安定し、面ごとの良し悪しが読めるようになってから開ける。
- 例外：認知目的（インプレッション価値）や、価値最適化が効く EC などでは有効な場合もある。

## 4. 自動オーディエンス拡張

- **0→1 / 成果数が少ない / 学習データが薄い段階では OFF が安全。**
- 十分な成果が溜まり、拡張に足るデータができてから検討する。
- なぜ：データが少ないと、拡張はコスト消化を最大化する方向に働きやすい。

## 5. ターゲティング（広く vs 狭く）

- **初期は「国 + 言語 + 年齢」程度の広めから**始め、Meta の学習に任せるのが無難。
- 細かい興味・職種指定は、精度が落ちている領域もあるため**単独依存しない**。自社データ（顧客リスト・サイト訪問者）由来のオーディエンスや、似ているユーザー（Lookalike）と組み合わせて補強する。

## 6. 入札戦略

- **初期は「最低コスト（上限なし）」で学習させる。** 最初から目標CPAで縛ると、学習データが足りず逆に出なくなる。
- **学習が安定したら「目標CPA」に切り替える**。「この単価で取れた人に似た人を探して」と Meta に方向づける発想。
- 上限を厳密に守りたい局面でだけ「入札上限」を使う（その分、配信量は落ちる）。
- 切り替え自体が学習リセット要因になるので、タイミングを選ぶ（learning-phase 参照）。

## 7. 予算の上げ方

- **配信が安定し、成果が読めるようになってから上げる。**
- 一気に増やすと学習がリセットされる。**段階的に**上げる（目安：一度に +20% 程度まで）。

## 8. サンプル数（勝ち負けの判定）

- **数件のデータで勝ち負けを決めない。** 統計的に意味のある量が溜まってから判断する。
- 週次レビューでは必ず「この判断に足るサンプル数か（low / medium / high）」を添える。

---

## 判定の出し方（Scale / Watch / Kill）

各広告・広告セットを、`config.md` で定めた自社の基準線に照らして3分類する。

- **Scale（伸ばす）**：CPA が目標を下回り、サンプル十分、疲弊兆候なし → 段階的に予算を寄せる。
- **Watch（様子見）**：判断に足るサンプルがまだない / 数値が境界 → 触らず観察を続ける。
- **Kill（止める）**：CPA が許容上限を超え、サンプル十分、改善見込みが薄い → 止めて予算を他へ。

> Scale / Kill の具体的な単価ラインは事業ごとに違う。`config.md` に自社の目標CPA・許容上限を定義し、それを基準に判定する。
